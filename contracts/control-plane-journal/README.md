# Control Plane journal contract

Version: `0.1.0-draft` (draft revision 3, 2026-10-18, decisions 23 and 31: optional profile members, registry label 0.2, see "Draft revisions"). Status: draft, proposal only. Not frozen (the first freeze is deferred by the owner), not part of `pder-v0.1`, not referenced by any `odes` code path, and not a qualification input. See `docs/engineering/ODES-INTERCOMPONENT-CONTRACTS.md` for the design and `contracts/execution-attempt-lifecycle/` for the sibling contract this one is modelled on and delegates to.

## Contract statement

This contract governs the boundary between the Control Plane run record and the components that read it:

- Producer: the Control Plane bounded workflow (`BoundedAuthorizationWorkflow` and `BoundedRecordStore` in `src/agent_control_plane/bounded.py`), which writes `BoundedRunRecord` (decisions, attempts, observations, reconciliations, refusals, resolution checks, closeouts, input time floors, and in journal mode the resolution journal `check_events` and `vocabulary_changes`).
- Consumers: the Replay bundle importer (`importers.py` `import_bounded_workflow`, `_validate_repaired_run`, `_effect_observation_history`; `refusal_evidence.py` `validate_run`, `extend_retained_inputs`) and, through Replay, the Evidence pack importer. The Governed Exchange reference runtime also reads the store (in-process today); this contract states the append-only property it relies on (`check_succession`). The runtime adapter (`engine/control_plane_adapter.py`) reads the workflow's results and records in process; that call is a coupling to remove, not a rule here.

Shapes and rules were read from Control Plane `26a7e659` (main) and Replay `7c6888f` (main), and checked against ten real runs captured from the Control Plane's own test helpers (synthetic proposals, deterministic clock). The pre-refusal Control Plane generations (the first bounded run record, which lacks `refusals`, `resolution_checks`, `closeouts` and `input_time_floors`) are not covered.

A conforming document states `contract: "control-plane-journal"` and `contract_version: "0.1.0-draft"` and carries the run record members. `schema.json` (JSON Schema draft 2020-12) defines members, types and enumerations. The rules below are the cross-record half, implemented by `validate.py`.

## Member model

Same model as the lifecycle contract.

1. Declared required members must be present: `contract`, `contract_version`, `run_id`, `decisions`, `attempts`, `observations`, `reconciliations`, `refusals`, `resolution_checks`, `closeouts`, `input_time_floors` (the producer always emits the last nine). `check_events` and `vocabulary_changes` are optional because the producer omits them when empty. Inside records, members the producer always writes are required; members it omits when unset (`reason_vocabulary_version`, `reopen_conditions`, `runtime_authority`, `read_state`, `generation`, `tenant_id`, `error`, `observed_at`, `destination_state` on an observation) are optional.
2. Every declared object has a closed member set. A member neither declared nor inside `extensions` is refused with `undeclared_member`, never dropped (V1 finding F-10).
3. Every declared object may carry `extensions`, an object whose member names match `^x-[a-z0-9][a-z0-9._-]*$` (`invalid_extension_key` otherwise). Consumers ignore extension members for contract logic, preserve them when re-emitting, and include them in any digest. Producer commitments (`effect_id`, binding digests) do not cover extension members; only a consumer digest of the whole export does.
4. Adding an optional declared member is a minor bump. Adding a required member, or changing the meaning of a status, is a major bump.
5. Enumerations are closed (decision item 6): a value outside them is `unknown_enum_value`, never coerced. Closed here: decision `result` (`authorized`, `hold`), `time_source`, attempt `status`, reconciliation `result` (`applied`, `observed_absent`, `safe_to_retry`, `hold`), observation `state`, closeout `original_status` (`attempted`, `unknown`, `failed`) and `observed_state` (`applied`, `partial`), resolution input `input_type` and `read_state`, check `stage`, journal `phase`, vocabulary change `kind`, and `reason_vocabulary_version` (`runtime-authority-reasons/0.1`, `runtime-authority-reasons/0.2`).

## Delegation to the lifecycle contract

Attempt lifecycle rows and journal protocol are the `execution-attempt-lifecycle` contract's rules (`missing_start_record`, `invalid_reconciled_marker`, `attempt_started_at_changed`, `repeated_record`, `journal_protocol`, `journal_unbound_completion`, `journal_check_reused`, `resolution_checks_out_of_order`). They are not restated: `validate.py` projects `attempts` to `control_plane_attempts` and `check_events` to `resolution_journal` and calls the lifecycle validator, re-emitting its codes with this document's paths. The member definitions shared with the lifecycle contract (`extensions`, `resolution_input`, `resolution_check`, `control_plane_attempt`; `journal_event` narrowed to the one vocabulary version) are identical, and a test pins that, and pins the lifecycle version this was reviewed against. `duplicate_check_id` is reported by this contract for every run. A vendored copy needs the lifecycle contract vendored beside it (same parent directory).

## Optional profile members (draft revision 2)

Three opt-in Control Plane profiles merged after this draft was written and add members to the run record: `operation-identity/0.1` (N1), `rule-revision/0.1` (N2) and `freshness/0.1` (N3). A fourth, `holder-inventory/0.1` (N5), adds no run-record member (a flagged class holds with the typed reason `holder_inventory_missing`; its inventory sits in the host profile). Before revision 2 this contract refused every record produced with a profile on (`undeclared_member`, `unknown_enum_value`, `schema_violation`), although the producer wrote it correctly (orchestrator finding F-3; the verifier and Replay refused all of them).

Revision 2 declares the profile members as OPTIONAL. The sets stay closed: a member that no profile owns is still `undeclared_member`, a profile member on the wrong object is still refused, and absent means valid. A record written without a profile has none of them, so it is byte-identical and every earlier fixture is valid or invalid exactly as before (a test pins the 80 earlier fixtures against their violations from before this revision, message included).

Declared as optional (26 members; `validate.py` lists them in `PROFILE_OWNED`, a test pins that table against the schema, and each description names its profile):

- Document lists, shape opaque here (rows are objects; the sidecar contract of the same name validates them): `operations`, `operation_renewals`, `attempt_joins` (operation-identity); `rule_revisions`, `rule_revision_refusals` (rule-revision); `age_extensions`, `age_extension_refusals`, `recovery_runs` (freshness).
- Row members: `operation_id` and `operation_issuer` on the `runtime_authority` block, `check_id` on refusals (operation-identity and freshness both write it); `rule_identity` on decisions and refusals (rule-revision); `evaluated_at` and `recorded_at` on decisions and attempts, `recorded_at` on resolution checks, `evaluated_at` and `deadline` on refusals, `evaluated_at`, `deadline`, `age_bound_seconds`, `extension_id`, `nonce` on journal events, `age_basis` on inputs (freshness).
- Enumeration values: journal event phases `overdue` and `expired`, input read state `nonce_mismatch` (freshness).

The schema uses only plain keywords (no vendor annotations), so a minimal interpreter such as the verifier's reads it unchanged. This contract checks presence, type and closedness of these members; the semantics (operation join agreement, rule digests recomputable, clock consistency, deadlines) stay with the three sidecar contracts, which validate them over the same run record. Nothing is restated here that a sidecar already enforces.

Three behavioural rules of this contract are made profile-aware, because the producer itself writes records they refused. Each relaxation applies only when the named profile member is present, and the refusal code is unchanged when it is not:

1. One lifecycle per effect (`second_attempt_for_effect`). An attempt that failed with `check_expired_before_dispatch` is not counted as a started lifecycle when a refusal of the same effect carries that reason and the freshness `deadline` member; one refusal excuses one attempt. A retry on a fresh check is then the effect's single counted lifecycle. Without the `deadline` member, or with another failure reason, two starts are still refused.
2. Observation clock (`observation_time_future`). Under freshness the observation clock is decoupled from the evaluation pass, so "future" is judged against the later of `evaluation_time` and `reconciled_at`; staleness stays relative to the evaluation. Without a freshness member the evaluation time is the only reference.
3. Journal on a lease hold (`journal_missing`, `vocabulary_version_without_journal`). A hold whose only reason is `check_lease_unavailable` and which carries the freshness `evaluated_at` may carry `reason_vocabulary_version` with no `check_events`: the lease is refused before a check is journalled. A second reason, or no `evaluated_at`, means a check ran or the record is a default one, and the journal rule applies.

One new rule, `profile_value_without_member`: a phase `overdue` or `expired` event carries the freshness `deadline`, and a `nonce_mismatch` input carries `age_basis`; without them the value is not the profile's. An `overdue` or `expired` event must follow an `opened` event of its check (`journal_protocol`). The profile times (`recorded_at`, `evaluated_at`, `deadline`) are timezone-aware like every other time (`timestamp_invalid`). `check_succession` also covers the profile lists (prefix rule), and `unfinished_checks` treats `expired` as terminal; `overdue` is non-terminal (a live check reported late), so an overdue check that never closes is still listed.

For the delegated lifecycle rules the projection leaves the profile members, the two profile phases and `nonce_mismatch` out (they are not the lifecycle contract's); a record without them projects exactly as before. The shared definitions stay identical to the lifecycle contract once the profile members are removed (a test pins that).

Not added, on purpose: cross-member rules that only the sidecars check today (operation id and attempt join agreement, rule digests recomputable from retained rows, the three clock orderings). The producer enforces some of those at write time (the sidecar READMEs say which), but this contract sees only the retained record, and the sidecar contracts already validate them with their own fixtures; restating them here would be a second copy that can drift. The dispatch that asked for this stream listed such rules as examples and said not to invent rules the producer does not enforce; the tracker (#43, X4 milestone) names the three behavioural rules above, and the code agrees with the tracker.

## Journal mode and the plain record

The resolution journal is on only under a runtime-authority profile. Then `check_events` is present and non-empty, every decision and refusal records `reason_vocabulary_version`, and every authorized binding carries `runtime_authority` (profile `runtime-authority/0.1`, with its six digest members). Without a profile none of those members appear (the producer omits them). The contract allows both; mixing is refused (`vocabulary_version_missing`, `runtime_authority_binding_missing`, `journal_missing`). Tenant bindings (`bounded-authorization-effect/0.2`) carry `generation` and `tenant_id` together or not at all (`tenant_binding_incomplete`); the generation is chosen by the producer's class, not by a proposal field.

An evaluation that never completed is valid evidence: a journal check that is opened only, or `interrupted` (closed by `recover_interrupted_checks` after the process died), means the authority evaluation did not complete. `unfinished_checks` lists them. A consumer reports such an evaluation as incomplete and never reads it as an authorization.

## Attestation-adjacent fields

- `effect_id` is the commitment (SHA-256, sorted compact UTF-8 JSON, `ensure_ascii` false, prefix `sha256:`) of `{proposal, grant_id, grant_revision}` taken from the binding (`invalid_effect_identity`). A held decision has no binding; its effect id commits the proposal alone and cannot be checked without the proposal, which is outside this boundary.
- Commitment members (`proposal_commitment`, `manifest_digest`, `payload_commitment`, `requirement_commitment`, `role_mapping_digest`, `record_commitment`, the `runtime_authority` digests) are `sha256:` plus 64 lowercase hex. They are producer-declared and unverified at this boundary (Replay records them as `attributed_claim`). A rejected observation is retained as attributed content, never as evidence of effect.
- The run record carries no signature, digest or attestation member. Its integrity is not asserted here. (The Control Plane's HMAC-signed replay bundle belongs to the generic policy-gate path and is a different artifact.)
- `input_time_floors` keys are commitments of `[input_type, input_id]`; values are timezone-aware times.

## Rules

Structural codes (schema, level S): `schema_violation` (type, required member, pattern), `undeclared_member`, `unknown_enum_value`, `invalid_extension_key`, `unsupported_contract_version`. The rest need the cross-record view (level L).

Decisions and references:

- Decision ids are unique, including verbatim repeats (`duplicate_decision_id`). Result `authorized` if and only if `reasons` is empty and a binding is present (`decision_result_inconsistent`). The operation horizon commits to the binding's proposal (`horizon_binding_mismatch`).
- An attempt or refusal names an existing decision (`dangling_decision_reference`), carries that decision's `effect_id` (`effect_id_mismatch`), and the decision is authorized with a binding (`attempt_on_unauthorized_decision`, `refusal_requires_authorized_decision`). Observations and reconciliations name an effect some decision has (`dangling_effect_reference`).

Attempts (beyond the lifecycle contract):

- Rows `attempted`, `failed`, `unknown` carry an empty acknowledgement (`attempt_acknowledgement_inconsistent`; the `reconciled_existing` marker is the lifecycle contract's). `error` is null on `attempted`/`acknowledged`/`partial`, a bounded reason code (`^[a-z][a-z0-9_]{0,63}$`) on `failed`, and `destination_outcome_unknown:<ExceptionName>` on `unknown` (`attempt_error_inconsistent`).
- An effect has at most one attempt lifecycle that starts with `attempted`. Observed absence never establishes retry eligibility after a prior attempt (`second_attempt_for_effect`); the single-row `reconciled_existing` shape is not a second lifecycle.

Observations and reconciliations:

- `retry_eligible` is always false (`reconciliation_retry_eligible`). A rejected or unavailable observation is recorded with result `hold` and non-empty reasons (`rejected_observation_not_held`); it may carry malformed content and never appears in `observations`.
- An accepted observation (`observation_accepted` true) has no reasons (`accepted_observation_has_reasons`), carries its observation (`accepted_observation_missing`) naming the reconciled effect (`observation_effect_id_mismatch`), is never in state `unknown` (`observation_state_unknown`); `applied`/`partial` carry `destination_state` naming the same effect (`destination_effect_id_mismatch`) and state (`destination_state_contradiction`); `absent` carries an empty one (`absence_has_destination_state`). These are the reasons the producer rejects an observation with, so an accepted record that violates one is not something the producer could have written.
- An accepted observation records the policy it was accepted under, max age above zero and tolerance not below zero (`observation_policy_missing`), has timezone-aware `observed_at` and `evaluation_time` (`observation_time_invalid`), is not later than `evaluation_time` plus the tolerance (`observation_time_future`) and not older than the maximum age (`observation_stale`).
- An accepted `applied` observation is result `applied`, `absent` is `observed_absent`, `partial` is `hold` (`reconciliation_result_mismatch`). `safe_to_retry` is declared by the producer type and never emitted; it is not in the contract's enum (decision 18-J4), so a record carrying it is `unknown_enum_value`.
- `observations` lists exactly the accepted reconciliation observations, per effect, in acceptance order (`observations_mismatch`).

Closeouts (append-only; they never rewrite attempt rows):

- One per attempt and observed state (`duplicate_closeout`); it names an attempt row with the same effect and original status (`closeout_lineage_missing`) and an accepted observation of that effect, state and `observed_at` (`closeout_observation_missing`). An attempt whose last row is still `attempted`, `unknown` or `failed` has a closeout for every accepted `applied`/`partial` observation of its effect (`closeout_missing`).

Refusals:

- Refusal ids are unique (`duplicate_refusal_id`), carry reasons (`refusal_without_reasons`), the original horizon equals the refused decision's horizon (`refusal_horizon_mismatch`), and every changed input is attributed to an actual read in `resolution_inputs` (`changed_input_unattributed`).

Inputs, times, journal, vocabulary:

- A missing input claims no record commitment (`missing_input_commitment`). The times Replay checks, and `reconciled_at` and `evaluation_time`, are timezone-aware (`timestamp_invalid`).
- A journal event naming a decision names an existing decision and its effect (`journal_lineage_mismatch`); a decision-stage check has no decision yet (null), an effect-stage check names its decision (`journal_stage_binding`). Resolution check ids are unique (`duplicate_check_id`).
- A row's `reason_vocabulary_version` is a registry label of the Control Plane (`runtime-authority-reasons/0.1`, 121 codes; `/0.2`, a 158-code superset); any other label is `unknown_enum_value`. A row labelled 0.1 holds none of the 37 codes only 0.2 registers (`reason_label_mismatch`, on decisions, refusals and check events; the set is `CODES_ADDED_IN_0_2` in `validate.py`, taken from the Control Plane's `schemas/runtime_authority_reasons_0_2.json` minus `_0_1.json` at main `6b8fb627`; 36 at `3755c71a`, plus `grant_revocation_recorded` of the opt-in terminal-revocation/0.1 profile, decision 33). The converse is not checked: the producer labels a row 0.2 only when it holds a 0.2-only code, but 0.2 is a superset, so a 0.2 label on 0.1 codes is accepted. Codes outside both registries are not judged.
- A vocabulary change is recorded once (`duplicate_vocabulary_change`), changes the version, and a split yields at least two codes (`invalid_vocabulary_transition`).

Succession (two exports of one run, `check_succession`, code `not_append_only`): every record list of the earlier export is a prefix of the same list in the later one, and `input_time_floors` never move backwards or lose a key. The Exchange reference runtime relies on this for its `attempts`, `observations` and `reconciliations` prefix check.

## Fixtures

Each fixture file is `{fixture_id, synthetic, expected_outcome, reason, [expected_refusal], [refused_by], document}`. `fixtures/valid/` must be accepted. `fixtures/invalid/` must be refused with `expected_refusal` as the only violation. The valid fixtures other than the extension, tenant and vocabulary ones are real producer runs (Control Plane `26a7e659`, synthetic proposals, fixed clock), with resolution inputs trimmed to a manifest and a grant read consistently across decisions, checks and journal, and ids, process owner and timestamps synthetic.

Each valid one is a real Control Plane run, unchanged (main `3755c71a`, re-captured 2026-10-18 after the registry split, decision 31-B; synthetic proposals, throwaway store, opt-in profiles switched on through the library as the Control Plane's own tests do; `acp run` has no profile options), with the two contract markers added and random ids, nonces and the process owner made synthetic. They come from the capture scripts of the three profile contracts plus `provenance/capture_profile_stack.py` (all four profiles on together, including a flagged class held for `holder_inventory_missing`); `provenance/build_fixtures.py` builds them. The 20 invalid ones are 19 single-defect mutations (`provenance/mutate_invalid_fixtures.py`, which stops unless exactly its one code results): closedness and types of the new members, a value without its member, an overdue event without an open check, profile times without an offset, and the three rules above each broken (a retry without the expiry refusal, a retry after an ordinary failure, an observation from the future under the profile, a lease hold with another reason, a lease hold without the profile clock), plus one derived tamper, `profile-op-grant-mismatch-held` (below). `provenance/differential_control_plane.py` loads every profile fixture through the Control Plane's own `BoundedRunRecord` (see Current conformance).

## Draft revisions

While the version is `0.1.0-draft` the draft label means no compatibility promise yet: a revision may break any consumer, and none is promised a notice period. Revisions are recorded here and in the decision log.

- Revision 2, 2026-10-18 (decision 23): the members, two check phases and one read state of the three opt-in profiles declared as optional (26 members, 3 enumeration values); the three rules above made profile-aware; rule `profile_value_without_member` added; `check_succession` covers the profile lists; `unfinished_checks` treats `expired` as terminal. Reason: the Control Plane's profile-on records were refused in full (orchestrator finding F-3; X3 and X4 journal checks), so the verifier and Replay could not read a record the producer wrote correctly. Compatibility: adding optional members is a minor-bump change; the relaxation of three rules and the new enumeration values would be major-bump class under the freeze rules, made here under the draft label without a version bump (the freeze is deferred). Every earlier valid record stays valid and every earlier invalid fixture is refused with the same violations; no earlier fixture changed. Tests changed: three sidecar tests that asserted the journal contract declares none of the profile members (operation-identity, rule-revision, freshness-clocks) now assert it declares them as optional; the shared-definitions test compares after removing the profile members; the rule-code coverage test needed a fixture for the new code.

- Revision 3, 2026-10-18 (decision 31): `reason_vocabulary_version` admits `runtime-authority-reasons/0.2` (enum on decisions, refusals and journal events; the lifecycle contract's shared `journal_event` already types it as a string); rule `reason_label_mismatch` added (a 0.2-only code under a 0.1 label). Reason: the Control Plane (N4, main `3755c71a`) labels a row 0.2 when it holds a 0.2-only code, and a 0.2-labelled record failed `v1.structure`. Fixtures: the 25 captured profile fixtures that hold a 0.2-only code had been captured at `128eaa5e`, before the split, and were first relabelled 0.1 to 0.2 on those rows by a script; they are now re-captured from the Control Plane at `3755c71a` (decision 31-B), which writes the labels itself, so every valid profile fixture is producer output again and the relabel script is removed; two valid (`reasons-0-2-label-with-a-0-2-code`, `reasons-0-2-label-on-0-1-codes`) and two invalid (`reasons-0-2-code-under-a-0-1-label`, `reasons-label-unknown-registry-version`) synthetic fixtures added. Not done: the 36 codes are copied into the validator, not read from the Control Plane at run time. Re-capture (decision 31-B): all 35 valid, 19 mutated invalid and 1 derived-tamper profile fixtures were rebuilt from `3755c71a` with `provenance/build_fixtures.py` and `mutate_invalid_fixtures.py` (their `control_plane_commit` and reason text changed; the `vocabulary_label` provenance note is gone); the documents of 33 of the 35 valid fixtures are identical to the relabelled ones, and two (`profile-rule-reports`, `profile-rule-host-rule-unadopted-does-not-gate`) differ only in the digest of the `runtime-authority-reasons/0.1` registry file, which changed in the producer. `profile-op-grant-mismatch-held` stays an invalid derived tamper. The sidecar contracts' own fixtures (operation-identity at `83b49b5`, freshness-clocks at `3f6a7668`) were not re-captured: they are unchanged output of the commits they name, and their `journal` rows carry 0.1 labels on some 0.2-only codes (no sidecar validator reads the label).

- Revision 4, 2026-10-18 (decision 39, same label): the delegated lifecycle rule `reasons_match` and its closed set `POST_JOURNAL_GATE_CODES` (see the lifecycle README). A check row may carry only its journal completion's reasons plus codes of that set. No fixture changed verdict.

- Revision 5, 2026-10-18 (decision 39, same label), three rules added; each counts or orders what a record already holds, so no member was added and every earlier valid record stays valid except the one synthetic fixture named below. `dispatch_license`: the effect-stage resolution checks that passed (no reasons) and were not consumed by a refusal are at least as many as the distinct attempt lifecycles (an `attempt_id` group; a `reconciled_existing` acknowledged-only lifecycle counts; an attempt refused at the dispatch gate is excused by its `check_expired_before_dispatch` refusal and not counted); every effect-stage check that carries reasons has exactly one refusal; a refusal for `authorization_binding_changed` or the expiry reason consumes a passing check. In journal mode the same is counted per decision from the completed effect-stage events (a completed effect event with reasons has a refusal for its decision; a decision's attempt lifecycles and refusals together do not outnumber its completed effect-stage checks). `reasons_minimum`: a completion's reasons include the floor implied by its own recorded input events (the table is `IMPLIED_REASONS` and `implied_reasons` in the lifecycle contract, listed in its README; the `nonce_mismatch` read state, which the lifecycle projection does not carry, is checked here). `causal_order`: an attempt does not start before its decision (`started_at` against `decided_at`, both evaluation time), a closeout does not rest on a reconciliation evaluated before the attempt it closes (evaluation time), and, where rows carry the freshness `recorded_at`, an attempt row is not recorded before its decision row and a closeout is not recorded before the attempt row it closes (service time); a service time is never compared with an evaluation time. These rules run after the reference, time and lifecycle rules, so a record with an earlier defect keeps reporting that defect. One valid synthetic fixture changed: `reasons-0-2-label-with-a-0-2-code` was derived from a held record by replacing its reasons with `holder_inventory_missing` alone while keeping the unreadable grant input; it now also carries the two reasons that input implies (`required_input_not_read`, `status_unreadable`), which is what the producer writes. Fixtures: 9 invalid (`dispatch-license-*`, `reasons-minimum-*`, `causal-order-*`, built by `provenance/mutate_round2_fixtures.py`).

## Input hardening (decision 32, 2026-10-18)

The reference validator never raises: any parsed JSON value gets a list of typed violations. Non-finite numbers (NaN, Infinity) and text that is not valid Unicode are refused as `schema_violation`; `main()` reads files with a strict loader (duplicate members, NaN, Infinity, overflowing numbers and non-UTF-8 input are refused, exit status 2, line `input_refused`); schema patterns match the whole string (`(?!\n)$` in `schema.json`) and times are ISO-8601 with ASCII digits and a UTC offset. No code, member or accepted form changed meaning; no code was added.
